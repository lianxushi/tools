自开发的常用工具集。每个工具单独放在一个目录里，优先做成浏览器能直接打开、不依赖安装和网络的页面。

## 目录约定

- 一个工具一个目录，目录名用小写英文和连字符，例如 `bbox-annotator/`。
- 工具自己的页面、说明和示例都放在该目录内，不要堆在仓库根目录。
- 能离线使用的工具，入口用该目录下的 `index.html`，并且不要在页面里引用远程脚本、字体或样式。
- 详细说明写在同目录的 `README.md`。需要一页短入口时，可以再放 `使用说明.md`，只写怎么打开，并链接到 `README.md`。两份文档不要各写一套可能不一致的操作细节。
- 新增或下线工具时，更新本文件的「工具列表」，使用相对链接。

## 新增工具

1. 新建目录，例如 `your-tool/`。
2. 放入可运行的入口（单文件工具就是 `index.html`）和一份按下面模板写的 `README.md`。
3. 若工具不需要安装，在说明里写明实际打开步骤，不要只写「见网上教程」。
4. 在本文件的工具列表加上名称、一句话说明，以及指向文档和入口的相对链接。
5. 不要在本仓库擅自添加开源许可证或 GitHub Pages 部署配置。

## 工具文档模板

每个工具的 `README.md` 使用中文，至少包含这些小节。没有的能力就写没有，不要把计划中的功能写成已经可用。

```markdown
# 工具名称

## 用途与适用场景
这个工具解决什么问题，适合谁用，不适合做什么。

## 功能
逐条列出当前真正可用的功能。

## 环境要求
操作系统、浏览器或其他运行环境。写明不需要哪些依赖。

## 下载与安装
怎样拿到文件。若免安装，写清免安装以及仍然要做的保存/打开步骤。

## 启动
从哪个文件、用什么命令或哪种打开方式启动。给出可以照做的步骤。

## 操作说明
按实际界面逐步说明。复杂工具在这里分小节写操作、快捷键和状态变化。

## 输入与输出
接受什么输入，产出什么文件或结果。字段、单位和示例放在这里。
示例数据要标明是示例。

## 隐私
会不会把用户文件或输入发到网络。只在工具会读取用户数据时保留这一节。

## 限制
不能做什么，数据会不会在刷新或关闭后消失，精度、配额、格式边界。

## 常见问题
针对上面这些行为，写使用时真正会遇到的问题。
```
